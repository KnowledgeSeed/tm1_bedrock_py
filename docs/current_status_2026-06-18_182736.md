## Release Assessment

The locally testable release scope is hardened and documented. Exception
handling is considered sufficient for the validated offline behavior:

- all 20 public functions in `TM1_bedrock_py.bedrock` have a common exception
  boundary;
- original exception types, tracebacks, and chained causes are preserved;
- credentials, secrets, SQL, and MDX are redacted or summarized;
- query collections and chained exceptions are also scrubbed;
- async worker failures are aggregated and cannot report partial success;
- rendered worker SQL and MDX are not written to error logs;
- SQL rollback and cleanup failures do not replace the primary failure;
- DB-API cursors do not need to support context-manager methods;
- temporary TM1 native views and subsets are cleaned independently;
- destructive source clears occur only after successful, non-empty exports.

This is not a claim that every live TM1 server, SQL driver, or deployment
configuration has been tested. See Known Limits.

## Known Limits

- Live TM1 contract and integration tests still require a configured Planning
  Analytics server and `tm1srv` test connection.
- Direct SQL routes should be validated against the exact production database,
  driver, permissions, and dialect version.
- Seven pandas `FutureWarning` messages remain in dimension normalization and
  test comparisons. They are not current failures but should be addressed
  before a future pandas upgrade.
- Sphinx HTML was not rendered locally because the current virtual environment
  does not contain `sphinx` or `docutils`.
- A distribution package was not built because the current virtual environment
  does not contain the `build` package.
- Caller-provided SQL, MDX, delete statements, and custom callables remain
  trusted executable configuration by design.

## Recommended Release Steps

1. Review `git diff` and confirm all dirty baseline changes belong in the
   release.
2. If available, run the live TM1 contract/integration tests.
3. Install documentation and build dependencies in a suitable environment:

   ```powershell
   .venv\Scripts\python.exe -m pip install -r docs\requirements.txt
   .venv\Scripts\python.exe -m pip install build
   ```

4. Render documentation with warnings treated as errors:

   ```powershell
   .venv\Scripts\python.exe -m sphinx -W -b html docs\source docs\_build\html
   ```

5. Build the package:

   ```powershell
   .venv\Scripts\python.exe -m build
   ```

6. Create a release branch, commit the complete accepted baseline, push, and
   run CI before publishing.
